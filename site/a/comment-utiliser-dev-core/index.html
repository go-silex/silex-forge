§01

Fil conducteur — pourquoi cet ordre

dev-core ne remplace pas le jugement d’un développeur : il structure le trajet problème → solution → code → preuve → livraison, et s’arrête à chaque porte où un humain doit valider.

Principe 1

Problème avant solution

Frame et Spec forcent à écrire ce qu’on résout et ce qu’on accepte comme done avant d’ouvrir l’éditeur. Moins de rework, moins de « on verra en PR ».

Principe 2

Effort calibré (tiers)

Un typo de 2 fichiers ne mérite pas une analyse multi-domaines. Un changement d’architecture ne se shippe pas sans sketch ni plan. Le tier choisit les étapes, pas l’inverse.

Principe 3

Vous êtes la gate

Frame, Spec et Plan demandent une approbation explicite. Review multi-agents, puis vous décidez fix / merge / stop. Rien d’irréversible sans votre feu vert.

Principe 4

Reprise d’état

Les artefacts sous artifacts/ (frames, analyses, specs, plans) sont la mémoire du ticket. Session coupée ? /dev #N reprend au bon step.

§04

Le fil /dev — tiers & progression

Au lancement, /dev lit l’issue, scanne l’état (artefacts, worktree, PR), propose un tier si nécessaire, affiche une barre Frame / Shape / Build / Verify / Ship, puis enchaîne le prochain step sans vous demander « on continue ? » entre chaque skill.

Tier Quand Chemin
S ≤3 fichiers, pas d’archi, risque faible recheck → implement → pr → validate → review → fix* → cleanup*
F-lite Scope clair, un seul domaine Frame → Spec → Plan → Implement → Verify → Ship
F-full Nouvelle archi, reqs flous, multi-domaines Frame → Analyze → Spec → Plan (+ sketch archi) → … → Ship

Ce que vous voyez

  • Titre + #issue + tier
  • Barre par phase (done / pending)
  • Next step explicite
  • Task list Claude Code = engagement de session

Gates humaines

  • Frame — approuver le cadrage
  • Spec — valider critères & découpage
  • Plan — valider micro-tâches (+ sketch F-full)
  • Review — fix / merge / stop
Pause plan → implement (F-lite / F-full) — après approbation du plan, le pipeline s’arrête et recommande /compact puis /dev #N pour repartir propre côté contexte avant de coder. Les tâches persistent dans la task list + l’artefact plan.
Worktree obligatoire — le code feature ne se fait pas sur main/staging. /dev bootstrappe un worktree .claude/worktrees/{N}-slug sur feat/{N}-slug avant frame / analyze / spec / plan / implement.
§05

Shape & Build — du problème au PR

Chaque skill est autonome : vous pouvez les lancer hors de /dev (/frame, /spec, /plan…). L’orchestrateur ne réécrit pas leur logique — il les enchaîne.

R
/recheck — avant tout travail Détecte drift git, symboles manquants, deps déjà résolues. Signal propre → silencieux. Signal feu → Proceed / Update / Close / Abort. Jamais skippé par /dev.
F
/frame — cadrer Problème, contraintes, scope, tier. Produit artifacts/frames/{N}-{slug}-frame.md. Gate d’approbation.
A
/analyze + /consensus — (F-full) Analyse technique profonde ; panel multi-experts (architect + 2 contextuels) si la décision est structurante. Artefacts sous artifacts/analyses/.
S
/spec — spécifier Critères d’acceptation, breadboard, slices, smart-splitting. Peut invoquer des experts. Gate d’approbation.
P
/plan — micro-tâches Plan d’implémentation, agents assignés, groupes de fichiers, dépendances. F-full : sketch d’archi (boundaries, data flow, state ownership, intégrations) avant le plan.
I
/implement — coder Exécute le plan via agents domaine (frontend / backend / devops / tester…). Recovery de conflits, abandon après 3 échecs d’une tâche.
PR
/pr — pull request Titre Conventional Commits, lien issue, guard rails. Puis /ci-watch pour le dashboard live des jobs.

§06

Verify & Ship — preuve, fix, atterrissage

La qualité n’est pas un « bonus en fin de PR » : review multi-domaines, hooks de sécurité, format auto, et un meta-orchestrateur pour lander sans friction.

Verify

/validate · /code-review · /fix

Validate — gates lint / typecheck / test / env / i18n / license.

Code-review — agents multi-domaines, Conventional Comments, scan secrets avant spawn, verdict APPROVED / CHANGES_REQUESTED.

Fix — auto-apply high-confidence, 1-by-1 pour le reste, max 2 itérations review↔fix.

Ship

/ship · /cleanup · /promote

Ship — commit → PR → review → fix → label reviewed + ci-watch. Idéal quand vous avez déjà codé hors /dev.

Cleanup — branches/worktrees orphelins, labels pipeline coincés, CI runs morts.

Promote — staging→main (repos staging-train). Sur trunk, le pre-flight seul ; l’auto-release coupe le tag.

Hooks toujours actifs — (1) bloque secrets / injections sur Edit-Write, (2) force bun run test plutôt que bun test (évite le spin CPU), (3) auto-format via stack.yml après chaque Edit/Write.

§09

Périmètre — ce que dev-core n’est pas

Clarifier le hors-scope évite de forcer le plugin hors de son job : exécuter le cycle de dev sur des issues déjà triées.

≠ triage d’issues

Labels size / priority / lane / type, blocked-by, parent/child : c’est le plugin séparé roxabi-issues (marketplace live). /dev lit les issues, ne les mute plus.

≠ board GitHub Projects V2

dev-core est issues-only. Pas de synchro de colonnes Project. La source de vérité d’avancement = artefacts + PR + labels pipeline.

≠ rewrite de votre stack

Le plugin s’adapte via stack.yml. Il n’impose pas Bun, Nest ou Vitest — il lit les commandes que vous lui donnez.

≠ merge sans humain

Auto-merge possible après label reviewed + CI green, mais la review multi-agents et l’approbation restent le contrat.

Sur un repo déjà GitHub-ready, enchaînez dans Claude Code :

claude plugin install dev-init
